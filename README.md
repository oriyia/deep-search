# deep-search

Скилл для ИИ-агентов (Claude Code и совместимых) — **универсальный глубокий поиск с ветвлением**:
бриф поиска → дерево веток (субагенты или последовательно) → проверка и сведение → хранилище
найденного, которое читают и человек, и агент.

Статус: скилл собран и установлен по [плану](docs/plans/2026-10-05-deep-search-plan.md) из
[спецификации](docs/specs/2026-10-05-deep-search-design.md); впереди обкатка на реальных поисках и
калибровка чисел. Язык скилла и шаблонов — русский.

---

## Что это

Агент, которого просто просят «найди», делает пару запросов и останавливается, верит сниппету
вместо страницы, принимает перепечатки за независимые подтверждения и каждый раз начинает с нуля.
deep-search задаёт порядок работы в три части:

1. **Подготовка** — бриф: что ищем, зачем, в каких границах и что считается ответом.
2. **Поиск** — дерево веток по типу вопроса, оценка источников по шкале A–F × 1–6, журнал,
   остановка по правилам, поатомная проверка ключевых утверждений, сведение одним автором.
3. **Сохранение** — хранилище в два слоя (свидетельства и выводы), которое переиспользуют
   следующие поиски, без свалки и без роста контекста.

Подробно, от общего к частному, — [docs/guide.md](docs/guide.md). Сравнение с другими
инструментами, что откуда взято и что своё, — [docs/comparison.md](docs/comparison.md).

## Установка

Нужен Python 3.10+ без сторонних библиотек; для текста страниц — `curl`, `pandoc`, `pdftotext`.

```bash
# 1. скилл: рабочая копия и ссылки из папок скиллов агентов — правка в репозитории действует сразу
#    (путь рабочей копии — от ~ или от /; -n: при повторе ln сообщит «File exists», а не создаст
#    ссылку внутри старой)
mkdir -p ~/.agents/skills ~/.claude/skills
git clone <url> <рабочая копия>
ln -sn <рабочая копия> ~/.agents/skills/deep-search
ln -sn ../../.agents/skills/deep-search ~/.claude/skills/deep-search

# 2. библиотека — общее хранилище найденного, отдельный git-репозиторий
#    (библиотека уже есть — init досоздаст в ней только watch/ для мониторинга)
python3 ~/.agents/skills/deep-search/deep_search.py init ~/research-library
git -C ~/research-library init -b main

# 3. путь библиотеки — в профиль оболочки (~/.zshrc или ~/.bashrc)
export DEEP_SEARCH_LIBRARY="$HOME/research-library"

# 4. по желанию — токен GitHub: 5 000 запросов к API в час вместо 60
#    (fine-grained, доступ «Public repositories (read-only)», без других прав)
export GITHUB_TOKEN=<токен>
```

В настройках Claude Code (`~/.claude/settings.json`; если файл уже есть — ключи добавить к
имеющимся) — путь библиотеки для агента, доступ к её папке и веб-инструменты без подтверждения
каждого вызова (фоновые ветки иначе встают на вопросе). `pandoc` и `pdftotext` достают текст
страниц и PDF, скрипт ветки зовут за `facts`, ведущий — за `doctor`, `lint`, `index`.
`Bash(python3:*)` не добавлять: это разрешение на любой код. Совпадёт ли правило на скрипт, если
агент напишет путь через `~`, ещё не проверено:

```json
{
  "env": {"DEEP_SEARCH_LIBRARY": "/home/<пользователь>/research-library"},
  "permissions": {
    "additionalDirectories": ["/home/<пользователь>/research-library"],
    "allow": [
      "WebSearch", "WebFetch", "Bash(curl:*)", "Bash(pandoc:*)", "Bash(pdftotext:*)",
      "Bash(python3 /home/<пользователь>/.agents/skills/deep-search/deep_search.py:*)"
    ]
  }
}
```

Проверка — в новой сессии агента `deep-search` есть в списке скиллов, а обе команды дают код 0:

```bash
python3 ~/.agents/skills/deep-search/deep_search.py doctor
python3 ~/.agents/skills/deep-search/deep_search.py lint --store "$DEEP_SEARCH_LIBRARY"
```

## История решений

Почему скилл устроен так, как устроен. Новое решение пишется сверху; отменённое не правится —
новая запись называет, что сменилось.

### 2026-10-11 · учёт поиска и карточка темы: что показала первая настоящая обкатка

Первый поиск уровня L на настоящей задаче (ранние сигналы вместо X и Discord) вскрыл пять мест,
где правила скилла расходились с работой:

1. Журнал ветки пишется строкой на каждое обращение наружу. `lint --run` предупреждает
   `log-undercount`, если ответ ветки насчитал больше запросов и источников, чем записано в журнале.
2. Пакет — серия однотипных запросов скриптом (история лент, страницы канала) — пишется одной
   строкой журнала `method: batch` с полем `count`; в задании ветки у него свой предел
   `batch_calls`, в `plan.md` — отдельная строка.
3. Предел задания ветки — 2 500 символов вместо 2 000.
4. `lint --run .` приводит путь к абсолютному: раньше у «.» не было имени, и сверка id брифа с
   именем папки давала ложное нарушение.
5. Шаблон карточки темы: «Ответ на …» — итог первым абзацем и разбор по подвопросам брифа (вывод,
   на чём держится, что ослабляет, ссылки на `C-…`); в «Объектах» — столбец «почему подошёл».

Почему. Ветки записали в журнал 57 строк, а в их же ответах насчитано почти 250 запросов и открытых источников, поэтому
бюджет по журналу был занижен в несколько раз, а прогон вышел за уровень L (185 вызовов при
60–120) из-за 94 запросов скриптом, которым в учёте не было места. Задание с перечнем известного и
пояснениями к бюджету ужималось до 2 000 символов в три-четыре прохода. Карточку по прежнему
шаблону человек прочитал как выжимку без разбора: причины выбора остались только в отчёте прогона.
Пересмотреть, если: `log-undercount` срабатывает на честных журналах (ответ считает источники
иначе); пакеты начнут подменять обычные вызовы; карточки перестанут укладываться в 300 строк.

### 2026-10-11 · ранние сигналы вместо X и Discord: 8 лент на пробу и правки набора

Проверка [research/2026-10-11-ai-early-signals](research/2026-10-11-ai-early-signals/README.md)
сравнила, когда о 13 выходах моделей (сентябрь — октябрь 2026) сообщили X и ленты набора. В набор
на пробу добавлены TestingCatalog, зеркала X-аккаунтов Anthropic и OpenAI на Bluesky, рассылка
Zvi и Telegram-каналы elkornacio, senior_augur, stuffyNLP, doomgrad — всего 76 лент. У
`anthropic-site` в `match.path` добавлен `/claude-`, порог `hn` снижен до 50 очков, у
`openai-news` записано, что время в ленте надёжно только как дата. `read_rss` берёт заголовок из
первой строки текста, если у записи нет `title`. X API, Nitter, xcancel, RSSHub для X, чтение
Discord и Telegram своим аккаунтом не взяты. Источники и причины — [docs/guide.md](docs/guide.md),
5.5.

Почему. На анонсах X опережает набор меньше чем на час (медиана поста лаборатории — +0,3 ч от
первого сообщения, Hacker News первым в 9 событиях из 13); X выигрывает только на утечках до
анонса и на постах, которых нет нигде больше, — под них взяты TestingCatalog и зеркала. Лента
Anthropic пропустила все 4 выхода моделей: их страницы лежат в корне сайта, вне разделов ленты.
Законный доступ к X — только платный API, обходы закрыты или нарушают условия площадок.
Пересмотреть, если: за 8 запусков TestingCatalog и зеркала не дадут ничего «только своего» — тогда
снова решать про X API; зеркала `xmirror.bot` перестанут работать; появится законный способ
читать объявления Discord без своего сервера.

### 2026-10-11 · одноимённые темы в двух хранилищах: какое правится

Если тема есть и в библиотеке, и в папке проекта, а выводы расходятся, поиск пишет новый вывод
только в хранилище из поля брифа `store`. Во втором хранилище агент меняет лишь статусы прежних
утверждений (перепроверено или `stale`) и оставляет в «Открытые вопросы» его темы ссылку на тему с
новым выводом, без содержимого. Раньше правила говорили только «неснятое расхождение — в
„Открытые вопросы“ обеих тем» и не называли, где появляется новый вывод. `references/store.md`
(«Запись», шаг 4), основная спецификация (6.5) и руководство (6.4, 6.6) поправлены.

Почему. Две полные копии одной темы снова разойдутся при следующем поиске, а перенос вывода из
папки проекта в библиотеку вынес бы сведения, которые не должны покидать проект. Заменить
утверждение другого хранилища (`superseded→…`) и нельзя: замена ссылается на строку того же реестра.
Пересмотреть, если: на обкатке темы-двойники накапливаются и человеку нужен способ слить их в одну.

### 2026-10-11 · связность хранилища: противоречия между файлами и забытые правки

`lint --store` теперь ловит и то, что раньше держалось только на аккуратности агента при
сохранении:

1. Ссылка карточки на утверждение, которого нет, которое заменено (`superseded`), опровергнуто
   (`retracted`) или ушло в архив, — нарушение `card-claim-ref`.
2. Вывод в «Ответ на …» без ссылки на `C-…` — предупреждение `card-answer-ref`.
3. Статус карточки против утверждений (`card-status`): `live` без живых утверждений — нарушение;
   `live`, когда все живые просрочены, и `stale` при живых непросроченных — предупреждения.
4. С прогоном (`lint --store <хранилище> --run <прогон>`) — сверка по предмету: живые утверждения о
   предмете, который прогон обновил, проверенные раньше даты прогона, в своей теме
   (`claim-subject`), в других темах (`claim-subject-shared`) и во втором хранилище, заданном
   `--also <путь>`; там же — одноимённая тема (`topic-twin`). Всё это — предупреждения.

Правила (`references/store.md`): `предмет` — одно имя объекта во всех темах обоих хранилищ; этап 0
сверяет тему, найденную в обоих хранилищах; предупреждения сверки решаются при записи — заменить,
перепроверить, пометить `stale` или оставить, неснятое расхождение — в «Открытые вопросы» обеих
тем. `watch` помечает запись темами библиотеки (`topics`), чьё другое название или имя объекта
встретилось в новости, и такая запись проходит фильтр интересов; дайджест ставит её в «Стоит
полного поиска» как `mode: update` темы, но карточку не правит. Основная спецификация, разделы 6.3–6.6
и 8.1, и спецификация мониторинга, разделы 2.5, 3.3, 3.4 и 4, поправлены.

Почему. Битые ссылки и сироты `lint` ловил и раньше, а противоречия появлялись иначе: карточку не
переписали после замены утверждения, старое утверждение забыли пометить заменённым, один предмет
обновили в одной теме и не тронули в другой, тема жила в двух хранилищах. Сверка по предмету
привязана к прогону: без него новое утверждение не отличить от перепроверенного, и
предупреждение висело бы постоянно. Новость о предмете темы важна и без слов интересов: она может
сделать вывод темы устаревшим. Карточку меняет только прогон, чтобы вывод опирался на проверенные
утверждения, а не на выдержку из ленты.
Пересмотреть, если: на обкатке `предмет` пишется по-разному в разных темах и сверка молчит;
`claim-subject` шумит на темах, где у одного объекта много независимых свойств; `topics` в `watch`
ловит чужие новости через общие слова в `aliases`.

### 2026-10-09 · мониторинг новинок: `watch`, `facts`, пресет `ai`, исключение для `init`

Мониторинг собран по [спецификации](docs/specs/2026-10-09-watch-design.md). `deep_search.py watch`
читает готовый набор лент скилла (`presets/ai-feeds.json`, 68 лент девяти типов) и добавки
библиотеки (`watch/feeds.json`), пишет найденное в `watch/new/<дата>.jsonl` и состояние в
`watch/state.json`; дайджест по сценарию `references/watch.md` агент пишет в `watch/digests/`.
`deep_search.py facts` — сводка о репозитории или пакете одним вызовом, у каждого значения адрес
запроса и путь к полю. Пресет `ai` — карта области для обычных поисков. Обе команды отвечают кодом
0, даже если часть лент или источников не ответила, и 2 — на ошибку вызова. `init` больше не
отказывает готовому хранилищу целиком: досоздаёт недостающее в `watch/` и ничего другого не трогает
(код 0); если и `watch/` на месте — код 2, как раньше. Решения, принятые при сборке, —
спецификация мониторинга, разделы 2, 3, 5, 6.2, 8; главное из них:

1. «Виденное» общее для всех лент; запись без даты при первом опросе ленты только запоминается.
2. Снимок страницы без ленты (`page`) хранится хешами строк, а не текстом.
3. Ленты одного сайта опрашиваются по очереди с паузой; токен GitHub уходит только к
   `api.github.com` и не идёт за редиректом.
4. Codex — через `releases.atom`: ответ API больше предела в 4 МБ. Reddit r/LocalLLaMA включён с
   оговоркой; пороги Hacker News и статей Hugging Face — 100.
5. `facts --json` — строки полей массивами по `columns`, в том же пределе 2 000 символов.

Почему. Скачать ленты, отбросить виденное и склеить дубли — механическая работа: в коде она
дешевле и одинакова при каждом запуске, а модель читает только новое. Набор в скилле обновляется
вместе с ним, а история «что видели» одна на все проекты — поэтому она в библиотеке. Без исключения
для `init` у библиотеки, созданной до мониторинга, не было бы способа получить `watch/`, не трогая
руками её остальное. Общее «виденное» и запись без даты только в память не дают одной новости
вернуться из другой ленты и ленте без дат выдать всю историю как новое. Хеши держат `state.json`
маленьким. Очередь к сайту и токен только для API GitHub — чтобы не получить блокировку и не
отдать токен чужому хосту.
Пересмотреть, если: обкатка покажет, что пороги (100 очков, 100 голосов, 8 запусков «на пробу», 3
провала) отбирают слишком много или мало; ленты с общим «виденным» теряют новости; `init` с
исключением понадобится для других папок хранилища.

### 2026-10-09 · источники: проверка, `apis.md`, мониторинг новинок

Источники-кандидаты проверены `curl` ([research/2026-10-09-sources-check](research/2026-10-09-sources-check/README.md)).
Прошедшие добавлены: GitLab, Codeberg и Forgejo/Gitea, Gitee, Repology, поиск по чужому коду,
Hacker News, Stack Exchange, Wikidata, Unpaywall, Europe PMC, pravo.gov.ru. Раздел «API по
областям» вынесен из `environment.md` в новый подфайл `references/apis.md`, разбитый по областям;
ветка читает «Общее» и раздел своей области. Какие источники используются, почему, что покрыто и
что не взяли — [docs/guide.md](docs/guide.md), 5.5. Мониторинг новинок ИИ входит в работу, хотя
спецификация (11) относила его ко второй версии: запуск вручную раз в несколько дней; скачать
ленты, отбросить виденное и дубли, отфильтровать — в коде (`deep_search.py watch`), агент тратит
токены только на новое. Telegram и другие внешние каналы — только авторские, которые первыми
пересказывают недоступное (X, Discord); источник держится, пока даёт уникальное.

Почему. `environment.md`, `sources.md` и пресет были у предела 200 строк и 12 000 символов, а ветка
читала `environment.md` целиком: 36 941 символ из 40 000. Разделы по областям дают ветке только
нужное — 37 536 символов вместе с новыми API. Поиск новинок механический: модель на нём дорога и
не нужна.
Пересмотреть, если: ветке регулярно нужны три и больше разделов `apis.md`; новые API перестанут
отвечать без ключа; `watch` покажет, что внешний канал не даёт ничего своего.

### 2026-10-05 · установка: путь библиотеки — переменная, веб-инструменты без подтверждения

Путь библиотеки задаётся только переменной `DEEP_SEARCH_LIBRARY` — в профиле оболочки и в `env`
настроек Claude Code; в файлах скилла и документации его нет, примеры — `~/research-library`.
WebSearch, WebFetch и `curl` разрешены без подтверждения. Токен GitHub — по желанию, через
`GITHUB_TOKEN`; `doctor` показывает остаток лимита и только сам факт, что токен задан.
Метапоиск SearXNG отложен: в v1 он не входит, а держать контейнер и следить за блокировками
поисковиков без нужды незачем.

Почему. Скилл один на все проекты, а путь — свойство машины: в репозитории, который может стать
публичным, ему не место. Переменная в двух местах видна и командам в терминале, и агенту,
запущенному не из оболочки. Без разрешений фоновая ветка останавливается на вопросе о каждом
запросе. Без токена GitHub API даёт 60 запросов в час на IP — один поиск по технологиям тратит их
за минуты.
Пересмотреть, если: появится второй агент со своим способом задавать переменные, или `curl` без
подтверждения начнут использовать не для чтения. SearXNG — поднять, если обкатка (тикет 11) или
оценка (тикет 12) не проходят из-за поиска: упираемся в 200 WebSearch на сессию, нужен поиск агенту
без встроенного или WebSearch не находит `known_items`.

### 2026-10-05 · уточнения волны 3–7

При написании подфайлов уточнены правила, которых в спецификации не было или которые были в ней
неоднозначны. Спецификация (разделы 1.4, 2.4, 4.3, 4.5, 4.6, 5.4–5.8, 6.2–6.6, 7.2), план («Общие
решения») и [docs/guide.md](docs/guide.md) поправлены.

1. Дата в улике — дата проверки; дата публикации источника — в `orig` после происхождения, нет её —
   «б/д».
2. Проверяющий берёт до 10 утверждений и проверяет строго по одному; цитату улики ему не передают.
   Протокол остаётся «да / частично / нет», а «нет» уточняется: «не говорит», «противоречит», «не
   открыта».
3. На контрольной точке 1 (L, XL) агент ждёт «ок», как на точке 0.
4. Ветка ставит букву улике, предварительный код и класс свежести утверждению; окончательную цифру
   ставит ведущий по уникальным `orig`. В ответе ветки — `findings[].fresh` и
   `log_summary.known_items_hit`.
5. `F<N>` — id находки внутри прогона до сохранения; реестр находок — раздел 4 отчёта; у отчёта нет
   frontmatter; формат таблицы `verify.md` задан.
6. Хранилище: у V0 нет даты свежести, у карточки из одних V0 `expires` — `—`; архив переносит
   карточку и её утверждения в `archive/topics/` и `archive/claims/`, источники остаются; колонка
   `keywords` INDEX — `aliases` и `keywords`; подтверждённое повторно утверждение меняет у строки
   только `проверено`, `свежесть`, `статус`; в `log.md` без прогона — `—`; списки во frontmatter
   карточки — строки через `, `.
7. `plan.md` прогона — до 4 000 символов; WebSearch считается в нём отдельно, ближе к 160 — API и
   curl или новая сессия.
8. «1» за отрицание — только если источник уровня A прямо пишет «не поддерживается», иначе «не
   найдено в …» и не выше 2; «по заявлению вендора» — атрибуция A1, содержание E4.

Почему. Дата проверки нужна для срока свежести, а дата публикации — для оценки самого источника; без
правила ветки писали бы то одну, то другую. Проверяющий без цитаты читает страницу сам, а не сверяет
готовый ответ; пачка до 10 и разбор «нет» по причинам дают ведущему, что делать с каждым вердиктом.
«Ок» на точке 1 — человек решает, на что тратить бюджет второго круга. Ветка не видит чужих веток и
не может посчитать независимость. `F<N>` и реестр в отчёте переживают сжатие контекста, а id
хранилища дают только при записи. Правила хранилища закрывают случаи, на которых `lint` и `index`
иначе разошлись бы с людьми. Предел `plan.md` держит возобновление дешёвым, а счётчик WebSearch не
даёт XL упереться в предел среды посреди раунда. Отсутствие упоминания — не отрицание, а
утверждение вендора о себе — факт только о том, что он это заявил.
Пересмотреть, если: обкатка (тикет 11) покажет, что проверяющему мало или много 10 утверждений, что
ветки ошибаются в классе свежести или что `plan.md` не укладывается в 4 000 символов на L и XL.

### 2026-10-05 · описание скилла — про проверяемость; `done_criteria` на S — одна строка

Описание (`description`) начинается с «Поиск по источникам, который выдерживает проверку» и
кончается «Не для свободного обзора-чтения». Проект в спецификации начинался с «Глубокий поиск» и
перечислял «deep research, исследование, обзор» среди триггеров. На уровне S `done_criteria` —
одна строка, а не рубрика из 3–8 пунктов. Спецификация, разделы 2.2 и 3.2, поправлена.

Почему. Слова «глубокий поиск» и «deep research» перехватывали бы вызовы встроенного
`/deep-research`, который пишет обзор для чтения без улик и без хранилища; отличие deep-search —
проверяемость, на ней и стоит описание. Уровень S — быстрый вопрос с мини-брифом из трёх строк:
рубрика сделала бы его дороже ответа.
Пересмотреть, если: на обкатке (тикет 11) скилл не поднимается на запросы «исследуй», «сделай
обзор», где он нужен, или итог S не удаётся проверить по одной строке.

### 2026-10-05 · требования к разработке — в `CONTRIBUTING.md`

В спецификации, раздел 2.1, правила разработки скилла лежали в отдельном файле для одного
инструмента. Теперь они в `CONTRIBUTING.md`, сформулированы для каждого, кто вносит изменения, а
служебные файлы инструментов разработки в репозиторий не входят. Раздел 2.1 спецификации и
[docs/guide.md](docs/guide.md), раздел 8, поправлены.

Почему. Репозиторий может стать публичным: правило, от которого зависит целость проекта, должно
приезжать с `git clone` к любому участнику, а личные настройки инструментов — оставаться в рабочей
копии.
Пересмотреть, если: у проекта появятся участники, которым нужны общие настройки инструмента
разработки.

### 2026-10-05 · спецификация v1

Скилл проектируется по [спецификации](docs/specs/2026-10-05-deep-search-design.md): ядро-маршрутизатор
с подфайлами по этапам, пресеты, шаблоны и скрипт проверок с тестами; бриф с обязательностью полей
по уровню и типу вопроса; дерево веток от типа вопроса и бюджеты S–XL; шкала A–F × 1–6; проверка
ключевых утверждений отдельным субагентом; хранилище в два слоя. Принятые решения и их источники —
спецификация, раздел 1.3.

Почему. Решения опираются на [исследование](research/2026-10-05-search-landscape/README.md) от
2026-10-05: инструменты и продукты, исследования агентного поиска, оценка источников, хранение и
переиспользование, контекст, ветвление и бюджет, систематические методы.
Пересмотреть, если: обкатка (тикет 11) или оценка «со скиллом / без» (тикет 12) покажут, что
бриф, ветвление или проверка не окупают своей цены.
