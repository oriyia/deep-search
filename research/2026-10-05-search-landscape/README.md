Вопрос: как сделать универсальный скилл качественного поиска с ветвлением из трёх частей — подготовка
(бриф), сам поиск, сохранение найденного, — взяв за основу собственную практику поиска технологий

## Коротко

- **Зрелые системы устроены одинаково:** уточнение → бриф или план (часто на согласование человеку) →
  ведущий раздаёт ветки с самодостаточным заданием → ветки возвращают сжатые находки → один автор
  сводит → отдельный проход проверки цитат [01, 07].
- **Агенты ломаются не на «найти факт», а на полноте, ранней остановке и работе с найденным.**
  В WideSearch отдельные факты находятся (item-F1 ≈80 %), а полностью верных таблиц ≤5 %; источник
  подтверждает утверждение в 39–77 % случаев; 3–13 % URL выдуманы [02, 03]. Перекрёстная проверка,
  полнота и проверка здравого смысла сами не возникают — в скилле это обязательные шаги.
- **Собственная практика уже содержит большую часть лучших практик:** задание до поиска, два прохода, журнал,
  шкалу надёжности, остановку по насыщению, «вывод только по открытой странице», «не найдено вместо
  догадки». Исследования их подтверждают [02, 08]. Добавить: «зачем» и «что считается ответом», цель
  полноты, тест на известных объектах, вторую ось оценки, поатомную проверку ключевых утверждений,
  хранилище между поисками [03, 04, 08].
- **Ветвление окупается только на разложимых задачах** (сбор, сравнение, независимые подвопросы),
  стоит ≈15× токенов чата и вредит на цепочках. Реализации сходятся на схеме «ведущий + один уровень
  субагентов, 3 ветки по умолчанию, глубина ≤2, ширина уровня вдвое меньше предыдущего» [07].
- **Контекст растёт от результатов, а не от текста скилла.** Чем больше вызовов в одном контексте, тем
  ниже верность цитат (−42 % от 2 до 150 вызовов). Отсюда: выжимка ветки ≤1,5 тыс. токенов, улики —
  в файлах, итог пишет один автор, проверка — в чистом контексте [02, 05, 07].
- **Накопления между поисками нет ни в одном продукте deep research.** Образец — «LLM Wiki»:
  неизменные свидетельства, переписываемый синтез, индекс строкой на страницу, журнал, lint.
  Переиспользование через индекс стоит ≈3–9 тыс. токенов против 11–34 тыс. на перечитывание старых
  отчётов [04].
- **Встроенные средства Claude Code ограничены:** WebSearch отдаёт заголовки и URL, WebFetch —
  пересказ малой моделью (для цитат и чисел не годится), 200 поисков на сессию вместе с субагентами.
  Текст страниц надёжнее брать через curl + pandoc, `pdftotext`, headless Chromium [01].

## Что нашли по частям скилла

### Подготовка

- Бриф пишут и утверждают до поиска; изменения по ходу — поправками с причиной. Так делают
  систематические обзоры (PRISMA-P), разведка (PIR, KIQ), OSINT (Berkeley Protocol), библиотечный
  reference interview [08]. Требования, выданные по частям, снижают качество в среднем на 39 % [02].
- Продукты задают 3–6 уточняющих вопросов только о том, что меняет направление, «Do Not Invent
  Preferences», незаданное помечают «без ограничения»; ChatGPT и Gemini показывают план на правку [01].
- Собственная форма задания на поиск покрывает ядро (PICO + критерии включения). Добавить:
  `decision_context`, `done_criteria`, `coverage_goal`, `known_items`, `assumptions`, `hypotheses`,
  `stop_rule`, `disclosure_constraints`; типовые направления поиска технологий — в пресет
  «технологии», в брифе — тип вопроса [08]. Поле «если данных нет»: продуктовые настройки по умолчанию
  склоняют к догадке [01].
- Тип задачи (трудный факт / перечень / обзор / сравнение / проверка) задаёт форму дерева, остановку и
  глубину проверки [02, 07]. `stakes` задаёт строгость подтверждения [03].
- Reference interview — 10 вопросов; главные — «какое решение примете» и «какой ответ примете».
  Бриф пересказывается человеку одним абзацем и подтверждается [08].

### Поиск

- Запросы: 2–5 слов, блоки понятий (синонимы через OR, блоки через AND), русский и английский;
  проходы «пробный → сбор терминов → основной → по ссылкам»; пустая выдача — повод переформулировать,
  а не «данных нет»; журнал — фильтр повторов [02, 08].
- Тест полноты на заранее известных объектах (≥80–90 %), самопроверка запросов по PRESS, поиск по
  связям по TARCiS (стартовые объекты, направление, круги, пока есть новое) [08] — это обобщение
  собственного «расширения по связям».
- Обязательный запрос-опровержение к ключевому выводу — обобщение поиска неудачного опыта [02, 08].
- Ветвление: на уровне одна ось; у ветки одна цель; ветка — только при ожидаемом выходе; уровни —
  раунды ведущего, без рекурсии (Jina отказалась от рекурсии: бюджет не делится) [07].
- Бюджет по сложности (Anthropic): простой факт — 1 агент и 3–10 вызовов; сравнение — 2–4 ветки по
  10–15; сложное — 10+ веток; на ветку мягко ~15, жёстко 20 вызовов; 15 % — резерв на сведение [01, 07].
- Остановка: условия достаточности, заданные до старта; насыщение (серия 2–3 шагов без нового — это
  «фрустрация» из исследований поиска, она же собственное правило насыщения); покрытие вопросов брифа
  («удовлетворение»); уход с ветки при отдаче ниже средней. Ветку закрывает ведущий [02, 07].
  «N подряд без нового» без оценки полноты ненадёжно — для перечней нужна контрольная выборка [07].
- Проверка утверждений работает поатомно, в свежем контексте без черновика, открытыми вопросами
  (на «да/нет» модель соглашается — CoVe); строгость проверяющего меняет долю «неподтверждённого» от
  3 % до 18 % — протокол фиксируется [02]. Механическая проверка открываемости ссылок снижает долю
  битых до ≤1 % [02].
- Специализированные источники прежде общего веба: context7 — документация библиотек; GitHub API,
  deps.dev, endoflife.date, OSV, Scorecard — ПО; OpenAlex, arXiv, Crossref — наука. Это открытые
  API [01].
- Найденный текст — данные, а не инструкции (prompt injection) [01].

### Оценка источников

- Две оси по образцу FM 2-22.3: надёжность источника A–F × подтверждённость утверждения 1–6, код
  `B2`; оценивается пара «источник × утверждение» (документация вендора — A для «опция есть в версии
  18», E для «самая быстрая») [03].
- Буква — по четырём вопросам: кто стоит → заинтересован ли → есть ли доступ к факту → есть ли метод.
  Цифра — по потолкам: только E — не выше 4, только D — не выше 3, один C — 3, один B — 2; «1» —
  открытый A нужной версии или два независимых A/B. На глаз оси сливаются [03].
- Подтверждение — по независимым происхождениям (`orig`), а не по числу упоминаний: синдикация и
  пересказы пресс-релиза — один источник; LLM принимают повтор за подтверждение [03].
- Свежесть — две даты и класс изменчивости V0–V3 со сроком перепроверки; просроченное — «6» [03].
- Пятиуровневая шкала типов источников переходит в A–E один к одному; «фильтр внимания» — потолок 3,
  «перечень заявлений вендора» — потолок 4, вывод по сниппету — «6» [03].

### Сохранение

- Два слоя: свидетельства (прогоны, реестр источников, реестр утверждений) неизменны, синтез
  (карточки тем, индекс) переписывается; устаревшее утверждение — `superseded`, а не правка [04].
- Единица знания — тема, а не прогон; отчёт прогона — снимок [04, 08].
- Утверждение хранится с источником, дословной цитатой и местом, оценкой, датой сверки и сроком
  годности; без цитаты не записывается; синтез источником не становится (ловушка «Convert to source»
  NotebookLM) [04].
- Ключ источника: DOI → канонический URL → sha256 текста; запись по тому же ключу заменяет прежнюю;
  ссылка хранится тройкой «оригинал, снимок, дата» [04].
- Против свалки: индекс ≤100 строк, карточка ≤300 строк, статусы, сроки годности, lint при каждом
  сохранении, архив скрыт от агента, отклонённое не удаляется («Пересмотреть, если») [04, 05].
- Где хранить: в проекте, в общей библиотеке (отдельный git-репозиторий, доступ через
  `additionalDirectories`) или в компилируемой вики. Рекомендована библиотека, проект — для
  конфиденциального [04]; принято: оба места, выбор в брифе.

### Контекст

- Claude Code: описание скилла всегда в контексте (≈100–150 токенов), тело — при вызове, подфайлы —
  по чтению; после сжатия контекста восстанавливаются первые 5 000 токенов тела каждого вызванного
  скилла, список скиллов и прочитанные подфайлы пропадают [05].
- Project-memory держит ядро ≤85 строк и ≤5 500 символов, главное — в первых 60 строках, подфайлы —
  по таблице «ситуация → файл», бюджеты проверяет код (`--self`, `--scenarios`) [05].
- Для поиска стадии складываются в одной сессии: полный прогон (бриф → 5 веток → сведение →
  сохранение) ≈ 74 500 символов (≈24 тыс. токенов). Отсюда бюджет возврата ветки и сценарий `full`
  в замере [05].
- 1 КБ Markdown ≈ 250–290 токенов (замер в 04); оценка «кириллица / 2,7 + прочее / 4,0» из
  project-memory не откалибрована [04, 05].

## Что не брать

- Монолитные research-скиллы: last30days — `SKILL.md` 260 КБ; academic deep-research — 52 КБ и
  53 файла [01].
- Облачные поисковые MCP по умолчанию (Exa, Firecrawl, Tavily): нужны платные ключи, запросы уходят
  третьей стороне. Подключаются пресетом или средой, когда появятся ключи.
- Рекурсивные субагенты: бюджет не делится, промежуточный вывод не виден [07].
- «Commit to your single most likely answer» (пресеты Perplexity) — против правила «не найдено
  вместо догадки» [01].
- Векторный поиск по хранилищу: grep по индексу дешевле и надёжнее до ~100–150 тем; дальше — FTS5 с
  токенизатором trigram [04].
- Из project-memory: скрытность от git, проверку следов агента, подъём скилла в каждой сессии, хуки
  как основу [05].
